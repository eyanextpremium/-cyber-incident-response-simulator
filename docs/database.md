# Database Documentation

## Overview

The Cyber Incident Response Simulator uses SQLite as its database backend. SQLite is chosen for its simplicity, portability, and zero-configuration setup, making it ideal for a training simulator that can run on a single machine.

## Database Location

The database file is located at:
```
data/simulator.db
```

This path can be configured in `config/simulator.toml`:
```toml
[database]
path = "data/simulator.db"
```

## Database Schema

### Sessions Table

Stores simulation session information.

```sql
CREATE TABLE sessions (
    id TEXT PRIMARY KEY,
    scenario_id TEXT NOT NULL,
    analyst_name TEXT NOT NULL,
    status TEXT NOT NULL,  -- 'active', 'completed', 'abandoned'
    started_at TEXT NOT NULL,  -- ISO 8601 timestamp
    completed_at TEXT,  -- ISO 8601 timestamp
    score REAL  -- Final score (0-100)
);
```

**Indexes:**
- `idx_sessions_status` on `status`
- `idx_sessions_started_at` on `started_at`

**Relationships:**
- One-to-many with Events
- One-to-many with Alerts
- One-to-many with Incidents
- One-to-one with Scores

### Events Table

Stores all security events generated during simulation.

```sql
CREATE TABLE events (
    id TEXT PRIMARY KEY,
    session_id TEXT NOT NULL,
    timestamp TEXT NOT NULL,  -- ISO 8601 timestamp
    source TEXT NOT NULL,  -- 'authentication', 'firewall', 'endpoint', etc.
    event_type TEXT NOT NULL,  -- 'login_attempt', 'connection', etc.
    message TEXT NOT NULL,
    host TEXT,
    source_ip TEXT,
    destination_ip TEXT,
    user_name TEXT,
    raw_log TEXT,  -- Original log line
    mitre_technique TEXT,  -- MITRE ATT&CK technique ID (e.g., 'T1110')
    is_malicious INTEGER NOT NULL DEFAULT 0,  -- Boolean
    FOREIGN KEY (session_id) REFERENCES sessions(id) ON DELETE CASCADE
);
```

**Indexes:**
- `idx_events_session_id` on `session_id`
- `idx_events_timestamp` on `timestamp`
- `idx_events_source` on `source`
- `idx_events_mitre_technique` on `mitre_technique`
- `idx_events_is_malicious` on `is_malicious`

**Relationships:**
- Many-to-one with Sessions
- One-to-many with Alerts (via event_ids JSON array)

### Alerts Table

Stores alerts generated by the detection engine.

```sql
CREATE TABLE alerts (
    id TEXT PRIMARY KEY,
    session_id TEXT NOT NULL,
    rule_id TEXT NOT NULL,  -- Detection rule identifier
    title TEXT NOT NULL,
    description TEXT,
    severity TEXT NOT NULL,  -- 'low', 'medium', 'high', 'critical'
    status TEXT NOT NULL DEFAULT 'new',  -- 'new', 'acknowledged', 'investigating', 'resolved', 'false_positive'
    event_ids TEXT NOT NULL,  -- JSON array of event IDs
    source TEXT NOT NULL,  -- 'detection_engine', 'manual', etc.
    created_at TEXT NOT NULL,  -- ISO 8601 timestamp
    acknowledged_at TEXT,  -- ISO 8601 timestamp
    resolved_at TEXT,  -- ISO 8601 timestamp
    FOREIGN KEY (session_id) REFERENCES sessions(id) ON DELETE CASCADE
);
```

**Indexes:**
- `idx_alerts_session_id` on `session_id`
- `idx_alerts_status` on `status`
- `idx_alerts_severity` on `severity`
- `idx_alerts_created_at` on `created_at`

**Relationships:**
- Many-to-one with Sessions
- Many-to-many with Events (via event_ids JSON array)

### Incidents Table

Stores incident records for tracking security incidents.

```sql
CREATE TABLE incidents (
    id TEXT PRIMARY KEY,
    session_id TEXT NOT NULL,
    title TEXT NOT NULL,
    description TEXT,
    status TEXT NOT NULL DEFAULT 'investigating',  -- 'investigating', 'contained', 'eradicated', 'recovered', 'closed'
    severity TEXT NOT NULL,  -- 'low', 'medium', 'high', 'critical'
    scenario_id TEXT,
    assigned_to TEXT,  -- Analyst name
    alert_ids TEXT,  -- JSON array of alert IDs
    created_at TEXT NOT NULL,  -- ISO 8601 timestamp
    updated_at TEXT NOT NULL,  -- ISO 8601 timestamp
    closed_at TEXT,  -- ISO 8601 timestamp
    FOREIGN KEY (session_id) REFERENCES sessions(id) ON DELETE CASCADE
);
```

**Indexes:**
- `idx_incidents_session_id` on `session_id`
- `idx_incidents_status` on `status`
- `idx_incidents_severity` on `severity`
- `idx_incidents_created_at` on `created_at`

**Relationships:**
- Many-to-one with Sessions
- Many-to-many with Alerts (via alert_ids JSON array)
- One-to-many with Evidence
- One-to-many with Response Actions

### Evidence Table

Stores collected evidence during investigations.

```sql
CREATE TABLE evidence (
    id TEXT PRIMARY KEY,
    session_id TEXT NOT NULL,
    incident_id TEXT,  -- Optional, can be collected without incident
    evidence_type TEXT NOT NULL,  -- 'log', 'file', 'network', 'memory', etc.
    title TEXT NOT NULL,
    description TEXT,
    data TEXT,  -- JSON data with evidence details
    source_host TEXT,
    collected_at TEXT NOT NULL,  -- ISO 8601 timestamp
    ioc_match TEXT,  -- IOC that matched (if any)
    FOREIGN KEY (session_id) REFERENCES sessions(id) ON DELETE CASCADE
);
```

**Indexes:**
- `idx_evidence_session_id` on `session_id`
- `idx_evidence_incident_id` on `incident_id`
- `idx_evidence_type` on `evidence_type`
- `idx_evidence_collected_at` on `collected_at`

**Relationships:**
- Many-to-one with Sessions
- Many-to-one with Incidents

### Response Actions Table

Stores response actions executed during incident handling.

```sql
CREATE TABLE response_actions (
    id TEXT PRIMARY KEY,
    session_id TEXT NOT NULL,
    incident_id TEXT,  -- Optional, can be executed without incident
    action_type TEXT NOT NULL,  -- 'isolate_host', 'block_ip', etc.
    target TEXT NOT NULL,  -- IP, hostname, user, etc.
    details TEXT,  -- Additional details
    success INTEGER NOT NULL DEFAULT 1,  -- Boolean
    performed_at TEXT NOT NULL,  -- ISO 8601 timestamp
    FOREIGN KEY (session_id) REFERENCES sessions(id) ON DELETE CASCADE
);
```

**Indexes:**
- `idx_response_actions_session_id` on `session_id`
- `idx_response_actions_incident_id` on `incident_id`
- `idx_response_actions_action_type` on `action_type`
- `idx_response_actions_performed_at` on `performed_at`

**Relationships:**
- Many-to-one with Sessions
- Many-to-one with Incidents

### Scores Table

Stores scoring results for completed sessions.

```sql
CREATE TABLE scores (
    id TEXT PRIMARY KEY,
    session_id TEXT UNIQUE NOT NULL,
    detection_score REAL NOT NULL,  -- 0-100
    investigation_score REAL NOT NULL,  -- 0-100
    containment_score REAL NOT NULL,  -- 0-100
    recovery_score REAL NOT NULL,  -- 0-100
    total_score REAL NOT NULL,  -- 0-100
    time_elapsed_secs INTEGER NOT NULL,
    calculated_at TEXT NOT NULL,  -- ISO 8601 timestamp
    FOREIGN KEY (session_id) REFERENCES sessions(id) ON DELETE CASCADE
);
```

**Indexes:**
- `idx_scores_session_id` on `session_id` (UNIQUE)
- `idx_scores_total_score` on `total_score`

**Relationships:**
- One-to-one with Sessions

### Assets Table

Stores network asset information (seeded data).

```sql
CREATE TABLE assets (
    id TEXT PRIMARY KEY,
    hostname TEXT NOT NULL,
    ip_address TEXT NOT NULL,
    asset_type TEXT NOT NULL,  -- 'server', 'workstation', 'network', etc.
    os TEXT NOT NULL,
    criticality TEXT NOT NULL,  -- 'low', 'medium', 'high', 'critical'
    department TEXT NOT NULL,
    status TEXT NOT NULL DEFAULT 'active'  -- 'active', 'inactive', 'decommissioned'
);
```

**Indexes:**
- `idx_assets_hostname` on `hostname`
- `idx_assets_ip_address` on `ip_address`
- `idx_assets_asset_type` on `asset_type`
- `idx_assets_criticality` on `criticality`

**Relationships:**
- No foreign key relationships (reference data)

## Database Initialization

The database is automatically initialized on first run by the `init_database` function in `src/database/connection.rs`.

### Initialization Process

1. Create database file if it doesn't exist
2. Create all tables with proper schema
3. Create indexes for performance
4. Seed initial asset data

### Seeding Assets

Initial asset data is seeded from `src/main.rs` with the following assets:
- Domain controllers
- Web servers
- Database servers
- File servers
- Mail servers
- Backup servers
- Workstations (various departments)
- Network infrastructure (firewalls, etc.)

## Database Operations

### Connection Management

The database uses a connection pool via `r2d2_sqlite` for efficient connection reuse:

```rust
use r2d2::Pool;
use r2d2_sqlite::SqliteConnectionManager;

let manager = SqliteConnectionManager::file(&db_path);
let pool = Pool::new(manager)?;
```

### Repository Pattern

All database operations go through the Repository pattern defined in `src/database/repository.rs`:

```rust
pub struct Repository {
    pool: DbPool,
}

impl Repository {
    pub fn new(pool: DbPool) -> Self {
        Self { pool }
    }
    
    // CRUD operations for each entity
    pub fn create_session(&self, session: &SimSession) -> Result<()>;
    pub fn get_session(&self, id: &str) -> Result<Option<SessionRecord>>;
    pub fn list_sessions(&self) -> Result<Vec<SessionRecord>>;
    // ... more methods
}
```

### Query Patterns

All SQL queries are defined as constants in `src/database/queries.rs`:

```rust
pub const INSERT_SESSION: &str = 
    "INSERT INTO sessions (id, scenario_id, analyst_name, status, started_at) 
     VALUES (?1, ?2, ?3, ?4, ?5)";

pub const GET_SESSION: &str = 
    "SELECT id, scenario_id, analyst_name, status, started_at, completed_at, score 
     FROM sessions WHERE id = ?1";
```

## Data Integrity

### Foreign Key Constraints

Foreign key constraints are enforced with `ON DELETE CASCADE` to ensure data consistency when a session is deleted.

### Unique Constraints

- `scores.session_id` is unique to ensure one score per session
- All primary keys are unique by definition

### Data Validation

Validation is performed at the application level before database operations:
- UUID validation for IDs
- Enum validation for status fields
- Timestamp validation for date fields
- Numeric range validation for scores

## Performance Considerations

### Indexes

Strategic indexes are created on frequently queried columns:
- Session ID (all related tables)
- Timestamps (for time-based queries)
- Status fields (for filtering)
- Severity fields (for prioritization)

### Query Optimization

- Use parameterized queries to prevent SQL injection
- Batch operations where possible
- Limit result sets for large queries
- Use appropriate data types

### Connection Pooling

Connection pooling reduces overhead:
- Default pool size: 10 connections
- Timeout: 30 seconds
- Max lifetime: 1 hour

## Backup and Recovery

### Manual Backup

The SQLite database can be backed up by simply copying the file:

```bash
cp data/simulator.db data/simulator.db.backup
```

### Automated Backup

Consider implementing automated backups in production:

```bash
# Daily backup with timestamp
cp data/simulator.db "data/backups/simulator_$(date +%Y%m%d).db"
```

### Recovery

To restore from backup:

```bash
cp data/simulator.db.backup data/simulator.db
```

## Migration Strategy

Since this is a simulator using SQLite, migrations are handled manually:

1. Backup existing database
2. Apply schema changes
3. Migrate data if needed
4. Test with sample data

For production, consider using a migration library like `sqlx-cli` or `diesel`.

## Troubleshooting

### Common Issues

#### Database Locked
- Ensure only one instance is running
- Check for long-running transactions
- Consider increasing timeout values

#### Performance Issues
- Check indexes are being used (EXPLAIN QUERY PLAN)
- Consider archiving old sessions
- Optimize complex queries

#### Corruption
- Run integrity check
- Restore from backup if corrupted
- Check disk space

### Debug Queries

Enable query logging in development:

```rust
tracing::info!("SQL: {}", query);
```

## Security Considerations

### Current State
- File-based SQLite (local access only)
- No encryption at rest
- No user authentication at database level

### Production Recommendations
- Encrypt database file
- Use PostgreSQL/MySQL with proper authentication
- Implement row-level security
- Regular access audits
- Backup encryption
